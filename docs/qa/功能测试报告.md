## 二、缺陷清单

### 🔴 BUG-01（严重）平均 RPS 虚高 5 倍 —— 所有 run 都受影响

**现象**：同一个 run，执行页 KPI 显示 `2494 rps`，接口统计表显示 `501 rps`。实测 9976 请求 / 19.9 秒 = **501 才是真值**。

**根因**：`services/influxdb.py:1019-1031`

```python
rps_q = "SELECT sum(\"count\") AS rps ... GROUP BY time(1s) fill(0)"
rps_values = [v for v in rps_values if v > 0]      # ← 过滤掉空桶
summary['avg_rps'] = sum(rps_values) / len(rps_values)
```

JMeter BackendListener **每 5 秒**上报一次聚合值，所以按 `time(1s)` 分桶后只有 1/5 的桶有数据，且每个桶装的是**5 秒的总量**。把 5 秒总量当每秒速率求平均 → 恒定虚高 5 倍。

`_on_finish`（`executor.py:1493`）优先采用 InfluxDB 汇总，只在 `total_requests==0` 时才回退 JTL，所以入库的就是这个错值。

**数学佐证**（两个 run 都精确吻合）：

| run | total_requests | InfluxDB rps 点数 | 入库 avg_rps | 商 |
|---|---|---|---|---|
| `6b89b5c627ab77b4` | 9976 | 4 | 2494.0 | 9976÷4 = 2494 |
| `ab7a1f4f87810525` | 999 | 7 | 142.7 | 999÷7 = 142.7 |

**已排除**：下载原始 JTL 验证，文件时间戳完全有序、span 19.918s，`executor._summarize_jtl` 与 `jtl_analysis` 两种算法在最终文件上都得 500.9 —— 问题只在 InfluxDB 这条路径。

**影响**：容量评估、版本对比、历史趋势里的 RPS 全部失真；虚高倍数 = BackendListener 上报间隔，改间隔会改变倍数。

**复现**：
```bash
curl -s .../runs/<run_id>/ | jq '.total_requests, .avg_rps'
curl -s .../runs/<run_id>/sampler-stats/ | jq '.[] | select(.label=="all") | .avg_rps'
# 两者应相等，实际差 ~5 倍
```

### 🔴 BUG-02（严重）生产未配置 Prometheus / Service / Environment —— 三个模块等于不存在

实测生产数据：

| 配置表 | 记录数 | 后果 |
|---|---|---|
| `PrometheusDataSource` | **0** | 服务诊断的 CPU/内存面板无数据源；Step 2 的「被压测服务」下拉是空的（ServicePicker 拉的是 `prometheus-sources/:id/services/`） |
| `Service` | **0** | Pinpoint 应用名映射不存在 → 拓扑/JVM/慢链路全部无从关联 |
| `Environment` | **0** | 每次预检都是「Environment 未配置，跳过 hosts 探测」，DNSCacheManager 注入形同虚设 |
| `AI_BASE_URL` 等 | **未配置** | `POST /ai-summary/` 返回 503「未配置 AI 端点」 |

4 个既有任务 + 1 个 QA 任务，`service_names` 全是 `[]`，`prometheus_source` 全是 `None`。

**性质**：不是代码 bug，是**上线配置缺口**——花了大量工作量开发的诊断、监控、AI 分析三块，在生产对用户完全不可见。

### 🔴 BUG-03（严重）scale-up / scale-down / ssh-refresh 三个端点无任何鉴权

`views.py:1821 / 1845 / 1874` 没有 `_check_agent_token` 保护（`register` / `heartbeat` 有）。加之全局 `AllowAny` + 平台无登录，**任何能访问该域名的人都可以**：

- 无限扩容压力机（消耗集群资源）
- `scale-down` 销毁正在跑压测的容器
- `ssh-refresh` 触发 `pkill -f ApacheJMeter`，**杀掉 SSH 压力机上正在执行的压测**

实测 `POST /load-generators/scale-up/ {"count":0}` → 返回 `400 count must be in [1,20]`，即**参数校验先于任何鉴权**，证实无鉴权。

> 注：`_check_agent_token`（`views.py:1767`）在 token 未配置时直接放行，而生产实测 token 为空（`PUT /load-generators/999999/heartbeat/` 返回 404 而非 401），所以 register/heartbeat 实际上也没保护。

### 🟠 BUG-04（一般）重复起 run 时报错误的原因，把用户引向错误方向

**现象**：任务已有运行中的 run 时，再次用**同一台**压力源起 run，返回
`400 部分压力源不存在 / 非 idle / 心跳超时（≥3min），请刷新列表`。

用户会去刷新压力源列表——但真正原因是任务已在运行。

**隔离验证**：换一台空闲 agent 起同一任务 → 正确返回 `409 该任务已有运行中的 run，请先取消` + `active_run_id`。

**根因**：`views.py:894` run 端点里，压力源可用性校验排在「任务是否已有活跃 run」之前。

### 🟠 BUG-05（一般）`register` 端点遇畸形参数直接 500

```bash
curl -X POST .../load-generators/register/ -d '{"pod_name":"x","port":"abc"}'
# → 500 Server Error（HTML 页面）
```

`views.py:1802-1806` 对 `port` / `cpu_cores` / `memory_gb` / `max_vusers` 直接 `int()` / `float()` 无 try，畸形值抛 `ValueError` → 500。应返回 400 + 字段说明。

> 附带正面发现：500 返回的是纯错误页无 traceback，证明**生产 `DJANGO_DEBUG=0` 生效**。

### 🟠 BUG-06（一般）布尔参数用 `bool()` 转换，字符串 `"false"` 被判为 True

```bash
curl -X POST .../runs/<id>/set-keep/ -d '{"keep":"false"}'
# → 200，实测 run.keep == True
```

`views.py:1088`（set-keep）、`views.py:1096`（set-baseline）用 `bool(request.data.get(...))`。任何非空字符串都是 True。前端目前传的是真布尔所以没暴露，但对外 API 语义是错的。

### 🟠 BUG-07（一般）p99 有两个口径，界面上显示不同数字且无说明

同一个 run：执行页 KPI `p99 = 123.2ms`（InfluxDB），接口统计表 `p99 = 117.0ms`（JTL 精确计算）。

根因：`influxdb.py:992` 用 `mean("pct99.0")` —— **对各上报区间的 p99 取平均**，统计上不等于整体 p99。JTL 侧走定长直方图精确计算。

两个数都不算"错"，但界面不说明来源，用户会怀疑数据可信度。建议统一以 JTL 为准，或在 UI 标注口径。

---

### 🟠 BUG-08（一般）预检磁盘空间显示 10,484,670 GB（约 10 PB）

预检输出 `✅ 磁盘空间 剩余 10484670.8 GB`，而实际 PVC 是 20Gi。`shutil.disk_usage()` 在该 CSI 存储上返回了无意义的值。

**后果**：`< 100MB 拒绝执行` 这道保护**永远不会触发**，PVC 真写满时不会被预检拦住，而是在压测中途以 JMeter 写盘失败的形式炸掉。

---

### 🟠 BUG-09（一般）预览的 XML 与实际执行的 XML 不一致

`GET /tasks/:id/preview-run-xml/` 调 `build_run_xml(task)` 时三个注入开关全为默认 False（`views.py:492`），实测生成的 XML 里：

- BackendListener 个数 = **0**（实际执行时会注入，且是按 TG 逐个注入）
- 无 DNSCacheManager（选了 Environment 也不体现）
- 无错误响应监听器

用户用它排查「为什么没有指标 / 为什么 hosts 没生效」时会被误导。界面上也没有"此预览不含运行时注入"的说明。

### 🔵 BUG-10（优化）`PUT /tasks/:id/` 绕过 PATCH 的全部业务逻辑

| 操作 | title 改 | 物理文件 rename | JMX 内容同步 |
|---|---|---|---|
| PATCH | ✅ | ✅ | ✅ |
| PUT | ✅ | ❌ | ❌ |

实测 PUT 后 `title="QA_冒烟_PUT改名"` 但 `jmx_filename="QA_冒烟_改名后.jmx"`，DB 与磁盘命名脱节。PUT 是 ModelViewSet 默认暴露的，没有 override。前端不用它，但 API 对外可达。

附带发现：`task.virtual_users` 改成 99 后，生成的 XML 仍是 `num_threads=1` —— 因为 Step 2 的 `thread_groups_config` 优先级更高。这是设计如此，但 `virtual_users` 仍被 StartRunModal 用于容量校验，两者不一致会导致按 99 VU 校验容量、实际只跑 1 VU。

### 🔵 BUG-11（优化）`TaskRun.load_generators` 未进序列化

run 详情里没有 `load_generators` 字段，前端无法展示"这次 run 用了哪几台压力源"。数据在 DB 的 M2M 里躺着（预检日志里能看到，但那是纯文本）。
